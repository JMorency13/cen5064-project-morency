# ADR-002: Layered architecture (routes → services → domain → data) for separation of concerns

**Date:** 2026-10-07
**Status:** accepted

## Context

The midterm requires a working slice that demonstrates a core use case (create event with conflict prevention) with business rules actually enforced. The business rule—preventing overlapping events at the same venue—involves multiple concerns: validating user input, checking for conflicts, persisting data, and returning HTTP responses.

Without a clear structure, business logic can become tangled across the codebase, making it hard to test, reuse, and maintain. The N-tier architecture pattern separates these concerns into independent layers: Presentation (UI), Service (HTTP and orchestration), Domain (business rules), and Data (storage).

## Decision

Organize the codebase into four layers:

1. **Routes** (`src/routes/events.js`): HTTP endpoints that handle incoming requests, parse input, and return responses. Routes do not contain business logic.
2. **Services** (`src/services/eventService.js`, `dashboardService.js`): Orchestrate the workflow—call Domain rules to validate, then call Data tier to persist. Services coordinate between Routes and the Domain/Data layers.
3. **Domain** (`src/domain/eventValidation.js`): Pure business rule functions that take data in and return validation results or conflict detection. The Domain tier does not know about HTTP, databases, or user sessions.
4. **Data** (`src/data/eventStore.js`): Repository interface for storage operations (`findAll()`, `save()`, `clear()`). Other layers call only these methods and never directly access storage details.

Each layer imports only from layers below it. Requests flow downward: Routes → Services → Domain and Data. Responses flow upward.

## Consequences

**Advantages:**
- **Testability:** Domain rules can be tested in isolation without mocking HTTP or databases. For example, `detectVenueConflict()` is a pure function that takes events and returns a boolean, so it's easy to unit test.
- **Reusability:** Services and Domain logic can be called from multiple Routes or future consumers (CLI, batch jobs, mobile API) without duplication.
- **Maintenance:** If business rules change (e.g., add a 15-minute buffer between events), I edit only the Domain tier; Routes and Data tiers remain stable.
- **Scalability:** Swapping the in-memory store for a database is a Data-tier change only. Services and Domain logic stay the same.
- **Clarity:** Each file has one responsibility, so new team members understand the codebase quickly.

**Disadvantages:**
- **More files:** Routing a single request through Routes → Services → Domain → Data requires more code and more function calls than a monolithic handler.
- **Over-engineering for MVP:** A small project might not justify four layers. However, the midterm rubric explicitly asks for N-tier architecture, so this is required.
- **Shallow layers:** The Domain tier currently has validation functions but no Entity classes. This is acceptable for the midterm; richer domain models can be added later.

**Mitigation:**
- I document the layer responsibilities in the README architecture section so the structure is clear.
- Tests cover the Domain tier heavily, so business rules are well-validated and easy to modify.
- I keep layers minimal (no unnecessary abstraction) while maintaining clear boundaries.
