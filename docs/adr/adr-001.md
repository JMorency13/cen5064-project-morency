# ADR-001: Use Express.js with in-memory store for rapid prototyping and testing

**Date:** 2026-10-07
**Status:** accepted

## Context

The midterm requires a working slice demonstrating a core use case (create event with conflict prevention) running end-to-end from screen through business logic to storage and back. The course scope is a single-semester project for one to two students. 

I need to validate the business logic (venue conflict detection, capacity enforcement) quickly without spending time on database setup, ORM configuration, or deployment infrastructure. My instruction and partner will clone the repo, follow the README, and run tests on their own machines—the system must work out of the box with zero external dependencies (no running database server, no authentication service).

Express.js is a lightweight, widely-used Node.js web framework that I can set up in minutes. An in-memory store (JavaScript object with array/map) persists data during a single server session and is sufficient to demonstrate the working slice.

## Decision

Use **Express.js** as the HTTP server and API framework, and implement the **Data tier as an in-memory JavaScript object** (eventStore) that maintains events in memory. The eventStore provides a repository interface (`findAll()`, `save()`, `clear()`) so the Service tier never directly accesses storage details.

Routes call Services, Services call Domain rules, and Domain rules remain independent of storage. This layering means swapping to a real database (SQLite, PostgreSQL, MongoDB) later is a change only to the Data tier, leaving business logic untouched.

## Consequences

**Advantages:**
- Zero setup: anyone clones and runs `npm install && npm start` with no database or service to configure.
- Fast feedback loop: tests run in milliseconds; no I/O wait.
- Clear separation of concerns: business rules in the Domain tier stay free of storage details.
- Portable: the system works on Windows, macOS, and Linux without changes.
- Data loss on restart is acceptable for a learning project; the README documents this limitation.

**Disadvantages:**
- Data does not persist between server restarts. I document this as a known limitation in the README and ADR-002.
- I do not practice with a real database or migrations, which is a trade-off for the course scope.
- In-memory storage scales only to a few hundred events on a typical machine; this is acceptable for a demo system.
- Concurrency and race conditions in simultaneous requests are not tested (in-memory store lacks locks). This is acceptable for the midterm.

**Mitigation:**
- The course scope is explicitly MVP (minimum viable product). Persistence can be added after midterm.
- I test the business logic thoroughly (conflict detection, capacity checks) so the core rules are correct regardless of storage.
- I clearly document the in-memory limitation in the README and this ADR so reviewers understand the trade-off.
